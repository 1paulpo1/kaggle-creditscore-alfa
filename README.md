# kaggle-creditscore-alfa

## 1. Описание
Учебный проект по кредитному скорингу на данных соревнования Kaggle
`alfa-bank-pd-credit-history`. В репозитории пять ноутбуков `00`–`04`,
образующих конвейер; общего `src/` нет. Запускать их нужно по порядку: `04`
использует `data/processed/03_summary.json`, который создаёт `03`.

## 2. Данные

- 3 000 000 заявок train (`id` 0…2 999 999) и 500 000 test (`id` 3 000 000…
  3 499 999); разбиение хронологическое: test идёт после train.
- 26 162 717 строк кредитной истории в train: строка — кредитный продукт,
  заявка — несколько строк. `id` идентифицирует заявку; отдельного
  идентификатора, общего для нескольких заявок, в данных нет.
- 60 признаков; 49 из них закодированы случайными номерами уровней. Пропусков 0,
  дубликатов `(id, rn)` 0; множества `id` в истории и в target совпадают.
- `flag = 1` у 3.55% заявок (106 442 из 3 000 000); по 20 корзинам `id` доля
  меняется в пределах 0.0279–0.0405.
- Числовые коды уровней — ярлыки, а не величины: средние и линейные корреляции
  по ним неинтерпретируемы. В основной модели используются агрегаты по истории и
  OOF-кодировка через цель, а не сырые коды; `02` — намеренный baseline на сырых
  колонках последней записи.

Данные не входят в репозиторий. `00` скачивает их с Kaggle после принятия правил
соревнования; ссылка и условия использования — в разделе 10.

## 4. Протокол оценки

- **Единица анализа — заявка.** Одна строка истории — кредитный продукт; `id`
  относится к заявке. Отдельного идентификатора, общего для нескольких заявок,
  нет, поэтому повторные заявки одного заёмщика проверить нельзя.
- **Обучение и выбор.** Всё, что связано с выбором, считается на заявках
  `id < 2M`. CV — expanding-window по фолдам 2–7: на фолде `k` модель учится на
  всех заявках с `id < k · 250 000`, проверяется на следующих 250 000; всего
  6 фолдов.
- **OOF-кодировка.** Партиция `k` кодируется статистикой партиций `0…k-1`;
  партиция 0 получает нейтральные нули и `cold_start = 1` (нет предыдущих
  OOF-партиций, а не отсутствие кредитной истории). Prior — **строчная**
  доля положительных строк, не доля заявок. Редкие и невиданные уровни получают 0.
- **Холдаут.** Отрезок `[2M, 3M)` — 8 блоков по 125 000 заявок. Метки холдаута
  читаются один раз, в финальной ячейке `03`; на нём даётся одна оценка уже
  зафиксированного набора. Холдаут не участвовал в выборе признаков,
  гиперпараметров или варианта.
- **Модель.** Один `HistGradientBoostingClassifier` с фиксированными
  гиперпараметрами: `max_iter=300`, `learning_rate=0.08`,
  `min_samples_leaf=200`, `l2_regularization=1.0`, `early_stopping=False`,
  `random_state=42`. 300 итераций — бюджет, а не доказательство сходимости;
  `n_iter_=300` означает, что лимит был достигнут.
- **`02` и `03`.** Оба используют один и тот же холдаут `[2M, 3M)` и те же
  блоки по 125 000. Но `02` — линейная модель на one-hot, а `03` — бустинг на
  OOF-агрегатах; поэтому разрыв между ними не изолирует вклад одного изменения.
- **Финальное обучение.** `04` учится на всех 3 млн заявок; это больше, чем 2 млн
  в оценке. Локальной оценки финальной 3M-модели нет: test не имеет меток в
  локальном пайплайне, а Kaggle-оценка не воспроизводится в репозитории.

## 5. Выбор признаков: лестница и упрощения

Сравнивались вложенные наборы:

- `control` — 92 признака: агрегаты log-odds, флаги `is_zero_*`, счётчики `nz_*`;
- `plus_counts` — 94: плюс `nz_loans530`, `nzshare_loans530`;
- `plus_recent_overdue` — 96: плюс `any_overdue`, `any_overdue_last3`;
- `plus_weighted_ladder` — 99: плюс `overdue_ladder`, `overdue_sev`,
  `overdue_sev530`.

Ступень принимается, если средний парный прирост по 6 фолдам больше одной
стандартной ошибки (SE по разностям) и положителен не менее чем в 5 из 6 фолдов.
При отказе выбор останавливается; отвергнутые ступени обратно не возвращаются.
Упрощение принимается, если текущий набор не лучше упрощённого по тому же
правилу.

| Вариант | Признаков | CV, среднее AUC | SD по фолдам |
|---|---:|---:|---:|
| `control` | 92 | 0.74348 | 0.00670 |
| `plus_counts` | 94 | 0.74738 | 0.00665 |
| `plus_recent_overdue` | 96 | 0.75028 | 0.00493 |
| `plus_weighted_ladder` | 99 | 0.74998 | 0.00487 |
| `without_n_records` | 95 | 0.74993 | 0.00517 |
| **`without_first`** | **79** | **0.75028** | **0.00549** |

Фактические решения:

- `plus_counts` против `control`: `+0.00390`, SE `0.00052`, 6/6 — принят.
- `plus_recent_overdue` против `plus_counts`: `+0.00290`, SE `0.00108`, 5/6 —
  принят.
- `plus_weighted_ladder` против `plus_recent_overdue`: `-0.00031`, SE
  `0.00026`, 1/6 — отклонён; выбор остановлен на `plus_recent_overdue`.
- `without_n_records`: текущий набор лучше на `+0.00036`, SE `0.00031`, 5/6 —
  упрощение отклонено; `n_records` остаётся.
- `without_first`: текущий лучше на `+0.00000`, SE `0.00035`, 4/6 — упрощение
  принято; `first_*` и `PAYM_first` удалены.
- Итог: `FINAL_VARIANT="without_first"`, 79 признаков. Варианта `full` в
  протоколе нет; это не «лучший по числу» выбор, а результат правила.

## 6. Результат

На зафиксированном наборе из 79 признаков холдаут `[2M, 3M)` даёт:

- среднее ROC AUC **0.739142**;
- SD по 8 блокам (`ddof=0`) **0.010409**;
- минимум `0.719149`, максимум `0.753993`;
- `n_iter_ = 300`.

Это оценка модели, обученной на 2 млн заявок. Финальная модель `04` обучается на
3 млн и локально не измерена. CV-среднее `0.750282` и холдаут `0.739142` не
сравниваются напрямую: CV — expanding-window на более ранних и меньших
подвыборках, холдаут — более поздний отрезок; блоки внутри холдаута
коррелированы.

Внешний Kaggle-бейзлайн соревнования (public/private на 2026-10-22):
`0.75478 / 0.74890`; источник — [leaderboard соревнования](https://www.kaggle.com/competitions/alfa-bank-pd-credit-history/leaderboard).
Это отдельное разбиение и отдельный расчёт; локальные числа с ним не вычитаются
и не выдаются за разложение разрыва на признаки.

### Проверка LightGBM (CV-only)

Дополнительно на тех же 6 expanding-window фолдах и 79 признаках, только на
`id < 2 000 000`, сравнивались HGB и LightGBM 4.7.0 при фиксированном бюджете
300 деревьев. HGB: `0.750282 ± 0.005492` (mean ± SD, ddof=0); LightGBM:
`0.749978 ± 0.004952`; парная разница `LightGBM − HGB = −0.000304 ± 0.000505`
(SE), LightGBM лучше в 4/6 фолдах. По заранее заданному правилу
(`Δ ≥ +0.001`, `Δ > SE`, выигрыш в ≥5/6) статус `keep_hgb`: финальная модель
остаётся HGB. Holdout для этого сравнения не использовался; это CV-only
проверка, а не статистический тест. Поле `holdout_labels_used` в артефакте
относится только к сравнению: финальный HGB по-прежнему обучается на всех 3 млн
заявок, включая этот отрезок. Время обучения в этом прогоне: HGB ≈200 с,
LightGBM ≈72 с на 6 фолдов; это ориентир, не бенчмарк.
Результат сохранён в `data/processed/04_model_comparison.json`; код — в `04`,
раздел 6.

## 7. `n_records` и бейзлайн

- В `02` абляция `rn`: с `rn` — `0.6740`, без `rn` — `0.6709`, дельта `+0.0031`
  (7/8 блоков; парная SD ≈ `0.0031`, SE ≈ `0.0011`). Блоки коррелированы, это
  описательная статистика, а не тест значимости.
- В `03` `n_records` как одиночный признак даёт AUC `0.4605`; после ориентации
  (`1 − AUC`) — `0.5395`. Это слабый сигнал, а не «хуже случайного»: знак
  означает, что более длинная история связана с меньшей долей `flag=1`
  (средняя длина 8.465 у `flag=0` и 7.894 у `flag=1`).
- `n_records` **оставлен**: упрощение `without_n_records` отклонено, текущий
  набор лучше на `+0.00036` (SE `0.00031`, 5/6). Это вывод правила, а не
  утверждение о пользе признака в другой модели.

## 8. Ограничения

- Холдаут — не Kaggle-test; test идёт дальше по времени и не оценён локально.
  Финальная модель на 3 млн заявок не измерена.
- Гиперпараметры не подбирались; проверен один временной порядок; блоки
  коррелированы, поэтому SD по блокам — не доверительный интервал.
- `ALPHA=200` и `MIN_LEVEL_ROWS=2000` не тюнились; это фиксированные решения.
- Калибровка не проверялась: средняя вероятность близка к базовой доле в `02`, но
  Brier score, logloss и calibration curve не считались.
- Кодировщик уровней — строчный, не на уровне заявки: строки с длинной историей
  получают больший вес. Это ограничение метода, а не проверенный оптимум.
- В данных нет отдельного идентификатора, общего для нескольких заявок; связи
  между повторными заявками не проверяются.
- `00-setup` перезапущен 2026-10-22; его outputs соответствуют текущему коду.
  Повторный прогон скачивает ~390 MiB и распаковывает датасет.
- Три идеи в репозитории не проверялись: число различных уровней у заявки,
  экспоненциальное затухание весов по `rn`, отдельные колонки `enc_paym_*` вместо
  среднего. Выводы ограничены тем, что реально измерено.

## 9. Воспроизведение и артефакты

Требования: `uv`, Python 3.12, ~3 ГБ свободного места (данные ~0.9 ГБ плюс
окружение и временные файлы), RAM ≥8 ГБ (пик `04` ~5.3 ГБ), аккаунт Kaggle и
OAuth-токен `~/.kaggle/credentials.json`.
Перед первым запуском примите правила соревнования на Kaggle. Данные и артефакты
в репозиторий не входят.

```sh
set -euo pipefail
uv sync
uv run kaggle auth login
for nb in 00-setup 01-eda 02-baseline 03-feature-analysis 04-features-training; do
  uv run jupyter nbconvert --to notebook --execute --inplace \
      --ExecutePreprocessor.timeout=7200 "notebooks/$nb.ipynb"
done
```

Флаг `--inplace` перезаписывает outputs в ноутбуках; после запуска `git diff`
покажет изменения.

Артефакты создаются локально (каталог `data/**` исключён из git):

- `data/processed/03_summary.json` — вариант, 79 колонок, CV/holdout, 8 блоков;
- `data/processed/04_model_comparison.json` — CV-only сравнение HGB и LightGBM;
- `data/processed/submission.csv` — 500 000 строк, `id` 3 000 000…3 499 999,
  NaN 0, md5 `12f10bbd4ac49a518acf53ad8f5dfbbb`.

`04` требует `03_summary.json`; поэтому полный порядок запуска — `00` → `01` → `02` → `03` → `04`.

Версии окружения: scikit-learn 1.9.1, pandas 3.0.6, numpy 2.5.4, pyarrow 26.0.0,
openpyxl 3.1.5, lightgbm 4.7.0 (dev), `SEED = 42`. Ориентир по времени на этой
машине: `00` — несколько минут вместе со скачиванием, `02` ~30 с, `03` ~26 мин,
`04` ~6–7 мин с CV-сравнением. Пик памяти `04` — около 5.3 ГБ; время и память
зависят от машины.
